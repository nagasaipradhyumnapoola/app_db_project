## 1. Core DBMS Concepts

### Q1: What is a DBMS (Database Management System)?
**Answer:**  
A Database Management System (DBMS) is specialized software that provides an interface between end-users or application programs and a structured database. It enables users to define, create, maintain, query, and control access to data. Key benefits include data abstraction, concurrency control, transaction management (ACID properties), data integrity, and centralized security.

### Q2: What is PostgreSQL?
**Answer:**  
PostgreSQL is a powerful, open-source object-relational database management system (ORDBMS). It is renowned for its reliability, feature robustness, and performance. It strictly adheres to SQL standards and supports advanced features such as complex queries, foreign keys, triggers, updatable views, transactional integrity (ACID), and Row Level Security (RLS).

### Q3: What is Supabase and how does it fit into DBMS?
**Answer:**  
Supabase is an open-source Backend-as-a-Service (BaaS) built directly on top of a standard PostgreSQL database. Unlike platforms that abstract data behind proprietary APIs, Supabase provisions a real, dedicated PostgreSQL database instance, complete with relational tables, SQL functions, triggers, and managed extensions. It provides real-time RESTful and WebSocket APIs, authentication services, and row-level security management over standard PostgreSQL.

## 2. Relational Constraints & Keys

### Q4: What is a Primary Key? How is it implemented in this project?
**Answer:**  
A Primary Key is a minimal set of attributes (columns) that uniquely identifies each tuple (row) in a relation (table). A primary key column must contain unique values and cannot contain NULL values.
- **In our project:** Column `id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` in the `public.students` table serves as the primary key.

### Q5: What is a Foreign Key? Why is it used here?
**Answer:**  
A Foreign Key is an attribute or combination of attributes in one table that references the primary key of another table, enforcing **referential integrity**.
- **In our project:** Column `teacher_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE` in the `public.students` table references the `id` column of Supabase's `auth.users` table. If a teacher account is deleted, the `ON DELETE CASCADE` rule automatically removes associated student records to prevent orphaned rows.

### Q6: What is a Unique Constraint? How is it applied?
**Answer:**  
A Unique Constraint ensures that all values in a column or combination of columns are distinct across the table. Unlike a primary key, a table can have multiple unique constraints.
- **In our project:** We defined a composite unique constraint:  
  `CONSTRAINT students_teacher_register_no_unique UNIQUE (teacher_id, register_no)`  
  This prevents a teacher from inserting two students with the same register number, while still allowing different teachers in separate departments to manage students independently without collisions.

## 3. CRUD Operations & SQL Syntax

### Q7: What does CRUD stand for?
**Answer:**  
CRUD represents the four fundamental operations performed on persistent storage:
1. **C**reate — SQL `INSERT`
2. **R**ead — SQL `SELECT`
3. **U**pdate — SQL `UPDATE`
4. **D**elete — SQL `DELETE`

### Q8: What are the exact SQL queries corresponding to the project's CRUD operations?

#### 1. INSERT (Create)
```sql
INSERT INTO public.students (register_no, name, department, year, email, teacher_id)
VALUES ('2024CS101', 'Alex Morgan', 'Computer Science', 2, 'alex@college.edu', auth.uid());
```

#### 2. SELECT (Read & Search)
```sql
-- Read all records for the authenticated teacher:
SELECT * FROM public.students
WHERE teacher_id = auth.uid()
ORDER BY register_no ASC;

-- Search for a student by Register Number:
SELECT * FROM public.students
WHERE teacher_id = auth.uid()
  AND register_no ILIKE '%CS101%'
ORDER BY register_no ASC;
```

#### 3. UPDATE
```sql
UPDATE public.students
SET name = 'Alex Morgan Jr.',
    department = 'Computer Science',
    year = 3,
    email = 'alex.jr@college.edu'
WHERE id = 1 AND teacher_id = auth.uid();
```

#### 4. DELETE
```sql
DELETE FROM public.students
WHERE id = 1 AND teacher_id = auth.uid();
```

## 4. Database Connectivity & Security

### Q9: How does the React frontend connect to the database?
**Answer:**  
The frontend connects using the official `@supabase/supabase-js` client library. The client is initialized with the project's public URL (`VITE_SUPABASE_URL`) and an anonymous/publishable key (`VITE_SUPABASE_PUBLISHABLE_KEY`). All client requests communicate securely over HTTPS with Supabase's PostgREST engine, passing an authorization Bearer JWT token received during teacher sign-in.

### Q10: What is Authentication vs Authorization?
**Answer:**  
- **Authentication:** Verifying **who** the user is (e.g., verifying the Teacher ID and password against `auth.users`).
- **Authorization:** Determining **what** actions or data an authenticated user is permitted to access (e.g., ensuring Teacher A cannot view or modify Teacher B's student records).

### Q11: How is password hashing handled? Why never store plaintext passwords?
**Answer:**  
Supabase Auth uses industry-standard adaptive hashing algorithms (such as **bcrypt** or **Argon2**) with individual cryptographic salts. Plaintext passwords are never stored in the database or exposed in logs. Storing plaintext passwords exposes user accounts to severe credential leaks during data breaches and compromises system integrity.

### Q12: What is Row Level Security (RLS)? Why is it superior to frontend filtering?
**Answer:**  
Row Level Security (RLS) is an enterprise database security mechanism in PostgreSQL. It evaluates security policies directly in the database engine for each query.
- Even if a malicious user alters frontend code or executes direct API calls, PostgreSQL will reject any query attempting to read or modify another teacher's rows because the database engine checks `auth.uid() = teacher_id`.
- Frontend filtering is merely visual; true security must reside at the database layer.

   > *"Finally, all operations are secured by PostgreSQL RLS ensuring teachers cannot access unauthorized records. Clicking Sign Out securely terminates the session."*
